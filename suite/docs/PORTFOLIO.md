# Presenting the projects honestly

## Evidence bundle per released product
- Live personal demo URL and read-only/synthetic entry path.
- Source repository, actual stack and deploy date/version.
- Short architecture + database diagram and security test evidence.
- 2–3 minute walkthrough; captions/transcript if recording.
- One real bug case study: failing test → root cause → minimal fix → regression.
- One post-scaffold feature change and why you made it.
- Known limitations, free-tier constraints and which tests were/weren't run.
- AI contribution/verification statement, not a fake authorship claim.

## Walkthrough script (150 seconds)
0–20: user/problem and one concrete workflow. 20–65: demonstrate actual feature including saving and reload in live mode. 65–100: show request/DB diagram and a security or domain test. 100–125: show one bug fix and test. 125–150: tradeoff, limits, next improvement. Don't spend two minutes on a landing page or tool/model names.

## Project positioning (use only after verified)
**ClientFlow:** Multi-tenant agency workspace demonstrating scoped client projects, task collaboration and private client portal. Differentiator: verified cross-tenant and client/internal isolation, not number of screens.

**SupportDesk AI:** Grounded customer support with retrieved evidence and human handoff. State retrieval-only vs real LLM mode clearly. Differentiator: transparent citations, tenant isolation, adverse-case evaluation and cost controls, not a claim of zero hallucinations.

**InvoiceHub:** Small-business invoicing with exact monetary calculations and auditable lifecycle transitions. Differentiator: tested rounding, idempotent payments, immutable issued invoice snapshot and concurrent numbering. Not tax-certified accounting software.

## Résumé evidence rules
Use “implemented” only for shipped behavior and “tested” only for executed evidence. Never invent user counts, uptime, revenue, performance improvements or employer endorsements. At foundation stage say “ClientFlow project-workbench prototype with tested validation,” not “production SaaS.” A work-in-progress project can still show useful engineering but must be labeled.

## Certificates
List certificate provider, exact course, earned date and verification URL only when obtained. In-progress courses should say in progress. Structured education supports the story; project tests and explanation prove practical skills. No guarantee a certificate substitutes for a degree or satisfies a particular employer's eligibility rules.

## Interview preparation per project
Rehearse the product LEARNING guide; open real code rather than memorized prose. Prepare to change one field and explain validation, SQL, auth, UI and testing impact. Be ready to say “I have not tested that yet” and describe the next verification step.
